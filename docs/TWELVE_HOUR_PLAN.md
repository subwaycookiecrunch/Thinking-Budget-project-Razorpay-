# Final twelve-hour execution plan

The clock starts when final submission work begins. Reorder around tasks already completed. Keep the last two hours free for publishing, video, and form errors; an unfinished ambitious model run is not a submission.

| Window | Work | Exit condition |
|---|---|---|
| 0:00–1:00 | Lock one problem, user, and product promise; audit every headline claim | README and demo tell the same evidence-backed story |
| 1:00–3:30 | Stabilize custom source review, resource allocation, evidence validation, and unresolved-file states | An input changed by the judge produces a new inspectable result |
| 3:30–5:00 | Run a genuine local or configured model; capture exact inputs, model, configuration, output, and usage | A saved real model run can be reproduced or its limits explained |
| 5:00–6:00 | Regenerate the deterministic benchmark and inspect misses/false positives | One versioned results file, matching docs, honest error list |
| 6:00–7:00 | Exercise timeout, invalid output, insufficient budget, and missing-source behavior | Each failure leaves a useful review state and an audit event |
| 7:00–8:00 | Fresh setup and browser verification; improve only blockers | Clean startup and complete critical demo path |
| 8:00–9:00 | Put final source and demo at user-authorized public destinations; verify signed out | Public URLs show the final build |
| 9:00–10:00 | Rehearse, record, and upload the pitch | A readable video under five minutes, containing a failure and limitation |
| 10:00–11:00 | Fill twelve application fields; check identity/availability manually | All required fields and files complete |
| 11:00–12:00 | Buffer for upload, deployment, form, or network failure | Submission receipt saved and all links rechecked |

## Cut first

Drop a new model training run, new benchmark domains, decorative graphs, extra tabs, and an elaborate paper before cutting reliable startup, real inference evidence, failure recovery, or the pitch video. Training cannot establish a credible improvement unless there is time to evaluate the actual adapter fairly afterward.

## Validation after submission

Recruit developers for a small review pilot; measure review completion time, accepted findings, false-positive handling time, and unresolved work. Use independently labeled real pull requests, freeze the routing policy before evaluation, compare with equal-budget and exhaustive baselines, and report confidence intervals. This is the route to a defensible value claim; the synthetic prototype does not provide it yet.
